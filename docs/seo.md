# Индексация публичных страниц

Сборка веб-версии:

```sh
npx expo export --platform web
EXPO_PUBLIC_API_BASE=https://platformaapp.ru node scripts/generate-public-pages.js dist
node scripts/generate-sitemap.js dist
```

Генератор создаёт HTML для каталогов, опубликованных статей, событий и
наставников. Информационные и правовые страницы получают отдельные title,
description и canonical. В каталогах есть обычные ссылки на все материалы;
контент доступен поисковому роботу без JavaScript.

`lib/seo-routes.js` содержит постоянные публичные маршруты. Новую публичную
информационную страницу следует добавить туда с метаданными и шаблоном.
Sitemap строится из `_seo-manifest.json`, созданного той же сборкой. Материалы
с `noindex` и статьи с canonical на другой URL в sitemap не включаются.
При сбое API сборка останавливается: неполная карта сайта не публикуется.

Админка, личные кабинеты, страницы авторизации и служебные маршруты не входят
в sitemap и получают `noindex`. `robots.txt` ограничивает обход этих маршрутов.

Автоматическая публикация настроена на `main`, а не на рабочую ветку.
Workflow также можно запустить вручную; ежедневный запуск в 03:00 UTC
обновляет HTML и sitemap для новых публикаций без изменения кода.
При копировании необходимо сохранять скрытые файлы (`dist/.`), включая
`.htaccess`. Сервер должен отдавать `/route/index.html` или `/route.html`
до SPA fallback на `/index.html`; правила для Apache и `_redirects`
формируются вместе со сборкой. Для nginx эквивалентно:

```nginx
location / {
    try_files $uri.html $uri $uri/ /index.html;
}
```

После публикации проверить на реальном домене:

- `robots.txt` и `sitemap.xml` возвращают HTTP 200 и соответствующий контент;
- URL из sitemap возвращает собственный HTML, title и canonical;
- HTML статьи содержит текст, а HTML каталога — ссылки на материалы без JS;
- страницы авторизации не включены в sitemap и имеют `noindex`.

В Google Search Console и Яндекс Вебмастере отправить
`https://platformaapp.ru/sitemap.xml` и запросить переобход важных страниц.
Точную причину исключения URL показывает проверка URL в кабинете поисковика;
наличие URL в sitemap и техническая доступность не гарантируют включение в индекс.

## Если `/sitemap.xml` показывает Unmatched Route

Это означает, что запрос получил HTML приложения вместо XML. Проверить, что
веб-сервер обслуживает `dist`, куда скопирован файл, и обрабатывает XML до
перенаправления в Expo/SPA. Наличие файла в GitHub само по себе не меняет
корневую директорию уже запущенного сервера.

`public/sitemap.xml` — резервная карта постоянных публичных маршрутов,
доступная также при обычном Expo export/start. Генератор заменяет её в `dist`
полной картой статей, событий и наставников. Она не заменяет обязательный шаг
генерации полной карты перед production-деплоем.

Проверки:

```sh
python3 scripts/verify-sitemap.py dist/sitemap.xml
python3 scripts/verify-sitemap.py https://platformaapp.ru/sitemap.xml --expect-file dist/sitemap.xml
```

Для nginx ресурс должен обслуживаться явно из того же каталога сборки:

```nginx
location = /sitemap.xml {
    root /dist;
    default_type application/xml;
    try_files /sitemap.xml =404;
}
```

Этот блок размещается перед общим SPA/proxy location. При другом пути
размещения сборки заменить `/dist` реальным корневым каталогом.

## XML из API независимо от frontend-сборки

Backend публикует `GET /api/seo/sitemap.xml` без авторизации. Ответ имеет
`Content-Type: application/xml` и строится из актуальных публичных данных БД.
Черновики, заблокированные/удалённые наставники и статьи с noindex исключены.
При подтверждённом владении доменом эту карту можно отправить в Search Console
напрямую. Для сохранения корневого адреса настроить nginx:

```nginx
location = /sitemap.xml {
    proxy_pass http://127.0.0.1:3000/api/seo/sitemap.xml;
}
```

Использовать реальный адрес backend из существующего `/api/` location.
Этот вариант не зависит от того, запущен frontend из `dist` или через Expo.
После изменения nginx проверить конфигурацию через `nginx -t`, затем
применить её штатным способом. Ошибка HTML в Search Console исчезнет только
после того, как опубликованный URL действительно станет возвращать XML.

Готовый полный nginx-конфиг с адресами вашего Docker-сервера находится в
`deploy/nginx.conf`. Единственное изменение к предоставленному конфигу —
точный `location = /sitemap.xml` перед общим `location /`.
Сначала развернуть backend с XML-эндпоинтом, затем применить nginx-конфиг
и проверить `/sitemap.xml` через `scripts/verify-sitemap.py`.
Файл в репозитории сам по себе не меняет действующий nginx на сервере.

## SEO событий

В карточке события в админке есть отдельный блок «SEO события» и кнопка
«Сохранить SEO». Он сохраняет метаданные без письма наставнику и изменения H1.
Поддерживаются slug, meta_title, meta_description, og_image/title/description,
canonical_url, noindex/nofollow, published_at, excerpt и alt обложки.
Теги остаются в форме правок; автор и био берутся из профиля наставника.
updated_at выставляется сервером при сохранении.

Перед первым запуском backend применить миграцию
`1792600000000-AddEventSeo`: она добавляет колонки и заполняет адреса и даты
у существующих событий. На production использовать штатный запуск миграций
(`npm run migration:run` после backend-сборки), не synchronize.
Затем развернуть frontend с генерацией публичных HTML.

Slug создаётся из названия при публикации события и не меняется при правке
названия. Старые UUID-адреса и предыдущие slug остаются доступными; клиент
переходит на текущий адрес, статический экспорт добавляет правила 301
в `_redirects` и `.htaccess` для поддерживающих их хостингов.
Собственные правила nginx нужно учитывать отдельно: он не читает эти файлы.
События с noindex либо canonical на другой URL исключаются из sitemap.
Сам nofollow не исключает страницу из индекса.

Публичный API, метаданные при переходах внутри приложения и API-sitemap
обновляются сразу после сохранения. HTML для роботов без JavaScript и
превью мессенджеров в текущей архитектуре статический: после изменения SEO
или публикации событий нужно повторить web-сборку с генерацией публичных
страниц и выложить dist. Одна обновлённая карта сайта HTML не пересобирает.
Сами поля не гарантируют включения URL в индекс Google.

## Предпросмотр статьи и диагностика Search Console

Telegram получает Open Graph из исходного HTTP-ответа, без выполнения React.
Правильные метатеги в браузерном DOM не доказывают, что их получил Telegram.
Генератор HTML использует `og_title`, `og_description` статьи и её обложку;
при пустых полях — SEO-заголовок, описание и обложку этой же статьи.

После публикации frontend выполнить проверку из каталога репозитория:

```sh
node scripts/verify-public-pages.js dist https://platformaapp.ru
```

Она сравнивает опубликованные title, canonical и OG с HTML той же сборки
для журнала, статьи, события и наставника. Проверяет HTTP 200 без редиректа,
дубли тегов и подмену конкретной страницы общей SPA-страницей. Workflow
выполняет эту проверку после загрузки файлов.

Если проверка не проходит:

1. Убедиться, что перед загрузкой выполнялись `generate-public-pages.js` и
   `generate-sitemap.js`. Обычного Expo export недостаточно.
2. Сверить директорию загрузки workflow (`FRONTEND_DEPLOY_PATH`, по умолчанию
   `/opt/frontend/dist`) с настоящим bind mount
   nginx. В показанной конфигурации `/opt/frontend/dist` смонтирован в
   `/usr/share/nginx/html`: это должна быть та же сборка, а не другой каталог.
3. В реальном `/opt/nginx/nginx.conf` обновить общий location:

   ```nginx
   location / {
       try_files $uri.html $uri/index.html $uri $uri/ /index.html;
   }
   ```

4. Проверить и перезагрузить nginx внутри контейнера:

   ```sh
   docker exec platforma_frontend nginx -t && docker exec platforma_frontend nginx -s reload
   ```

5. Проверить HTTP-ответ конкретной статьи, включая запрос без JavaScript:

   ```sh
   curl -sS -L -A TelegramBot 'https://platformaapp.ru/journal/SLUG' | sed 's/></>\n</g' | rg 'title>|canonical|og:|robots|seo-content'
   ```

Telegram может кешировать уже полученный предпросмотр: после проверки
исправленного HTML обновить превью через официальный @WebpageBot.
Это не требует изменения slug статьи.

Sitemap API отражает публикации сразу, HTML — после workflow (также есть
ежедневный запуск). Для немедленного предпросмотра новой публикации запустить
workflow вручную и дождаться успешной проверки HTTP. Добавление в sitemap
не создаёт HTML и не означает включение в индекс Google.

Статусы Search Console следует проверять по конкретным адресам:

- «Копия, канонический вариант не выбран»: сравнить исходный HTML, canonical,
  URL со слешем/без него, параметры и старые адреса. У самостоятельной статьи
  должен быть собственный canonical. Сходство темы не делает статьи дублями.
- «Обнаружена, не проиндексирована»: Google знает адрес, но ещё не выполнил
  нужное сканирование. Проверить доступность, ссылки из каталога и исходный
  контент, затем запросить индексирование важных URL. Срока гарантии нет.
- «Просканирована, пока не проиндексирована»: проверить HTML и выбранный
  Google canonical, затем полноту и уникальность материала. Это не доказывает
  техническую ошибку само по себе.
- «Ошибка переадресации»: нужен URL и полная цепочка HTTP-ответов; исключить
  циклы и неверные назначения.
- «Страница с переадресацией» и «Вариант страницы с canonical» обычно
  исключаются намеренно. Индексироваться должна целевая основная страница.

После публикации исправлений проверить URL в Search Console в реальном
времени, запросить индексирование приоритетных страниц и запустить проверку
исправления для соответствующей группы ошибок. Это не гарантирует индексацию.


## Исправление пути production-деплоя

`Upload dist via scp` загружает сгенерированную сборку в
`/opt/frontend/dist` — показанный host bind mount контейнера nginx.
Для другого сервера задать GitHub Actions repository variable
`FRONTEND_DEPLOY_PATH` (абсолютный путь, заканчивающийся на `/dist`).
Workflow проверяет существование каталога перед загрузкой и затем проверяет
публичный HTML без JavaScript. Перезапуск nginx сам по себе не создаёт HTML
статей и не переносит сборку из другого каталога.

Если HTTP-ответ статьи содержит `canonical=https://platformaapp.ru/` и
заголовок главной, проблема в выдаваемом HTML; обновление Telegram-кеша
до исправления сервера не поможет. Для диагностики существования файла:

```sh
docker exec platforma_frontend sh -c 'ls -l /usr/share/nginx/html/_seo-manifest.json /usr/share/nginx/html/journal/mariinskiy-teatr-kak-turisticheskiy-attraktsion-pochemu-pohod-tuda-bolshe-ne-svyazan-s-muzykoy.html /usr/share/nginx/html/journal/mariinskiy-teatr-kak-turisticheskiy-attraktsion-pochemu-pohod-tuda-bolshe-ne-svyazan-s-muzykoy/index.html'
```

Отсутствие файла означает, что материал не сгенерирован в обслуживаемой
сборке. При наличии файла сравнить его title/canonical с HTTP-ответом и
проверить активный `nginx -T`, права чтения и соответствие server/location.
301 с `/journal` на `/journal/`, за которым следует 200, не является циклом.
Но такой ответ не соответствует новой конфигурации `try_files`, которая
сразу обслуживает сгенерированный `journal.html` по `/journal`.
